# 采集器串口通讯协议规范（升级通道）

> 依据 Boot 工程（GD32F303 采集器 Bootloader）源码整理。
> 参考代码：`source/Collector/Collector.c`（命令解析/应答）、`source/Collector/ComProtocol.c`（PPP 帧层）、
> `source/Collector/TEA.c`（加密）、`source/Collector/CRC32.c`（校验）、`source/Collector/Update.c`（升级状态机）、
> `source/BBJBootUpgrade/LinkRS232.c` + `source/include/UpLink232Def.h`（PC 刷机协议）。
> 多字节数值除特别注明外均为**小端（Little-Endian）**。

---

## 1. 总览

采集器对外串口上共有**两套协议**：

| 协议 | 用途 | 使用者 |
|---|---|---|
| 协议 A：采集器命令协议（0xAA 帧） | 平台/主机向采集器推送 ARM / DSP 固件 | 采集器 Boot 上电轮询执行 |
| 协议 B："Link" 刷机协议 | PC 上位机刷写 APP / 配置表 / Logo / 硬件配置等 | Boot 的 `LinkRS232Upgrade()` |

一次完整升级的典型时序：**上电 → Boot 用协议 A 询问 ARM 固件 → 推 ARM 固件 → 询问 DSP 固件 → 推 DSP 固件 →（3 秒后）协议 B 刷机窗口约 1 秒 → 跳转 APP**。

---

## 2. 物理层（协议 A）

| 项目 | 参数 |
|---|---|
| 接口 | USART2，PB10=TX，PB11=RX（TTL） |
| 波特率 | **9600**，8 数据位，1 停止位，无校验 |
| 接收方式 | 中断收单字节入环形队列（深度 1088 字节） |
| 最大帧长（转义后） | 1088 字节（`FRAMLEN`） |

> 9600bps 下一包 1042 字节数据线上传输约 1.2s，升级速度约 0.9KB/s，属正常现象。

---

## 3. 协议 A · 第一层：PPP 转义帧

字节流以 `0x7E` 为帧定界符，帧内出现的控制字节需转义（与标准 PPP 一致）：

| 线上字节序列 | 还原为 |
|---|---|
| `7E` | 帧开始 / 帧结束 |
| `7D 5E` | `7E` |
| `7D 5D` | `7D` |
| `7D` + 其它 | 非法，丢弃整帧重新等待 |

发送封装 / 接收还原伪代码：

```
发送: out = [7E]; for b in payload:
        if b==0x7E: out += [7D,5E]
        elif b==0x7D: out += [7D,5D]
        else: out += [b]
      out += [7E]
接收: 收到 7E 且已有数据 → 本帧结束；帧长 > 1088 → 丢弃
```

## 4. 协议 A · 第二层：命令帧明文格式

转义还原、解密后的命令帧（`CollectorCmdDef`，packed）：

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `header` | 固定 **0xAA** |
| 1 | 2 | `CmdLen` | u16 LE。`CmdLen = ALIGN4(8 + param2数据长度)`，即 8 字节帧头+数据区长度（含 CRC 前的全部数据，对齐到 4） |
| 3 | 1 | `cmd` | 命令字 |
| 4 | 2 | `param1` | u16 LE。升级命令中 1=ARM，2=DSP |
| 6 | 2 | `param2` | u16 LE。data 区有效字节数 |
| 8 | CmdLen-8 | `data[]` | 命令参数 |
| 8+CmdLen | 4 | `crc32` | u32 LE。覆盖帧前 `CmdLen` 字节（帧头+data 区） |

整帧总长 = `8 + CmdLen + 4`。接收方校验规则（`Collector.c: InstructionProcess`）：

1. `header == 0xAA`；
2. `CmdLen >= 8` 且 `CmdLen % 4 == 0`；
3. CRC-32 校验通过（算法见 §6）。

任一不满足 → 静默丢弃（无任何应答）。

## 5. 协议 A · 第三层：加密（双层 TEA-CBC）

### 5.1 密钥

```c
FrameKey[4] = {0x3e23e3fe, 0x4cc197ac, 0x074db01f, 0x42fee1bd};  // 外层/基础密钥
FwKey[4]    = {0xfe23213f, 0xac89cd44, 0x12bcfdcc, 0xede19348};  // 固件载荷密钥
```

### 5.2 算法

- 分组密码：**标准 TEA**，32 轮，`delta = 0x9E3779B9`（代码里解密侧常量拆成两半相加，数学上等价）。
- 链接模式：**CBC，初始向量 IV = 0**（每 8 字节块先与前一块密文异或再 TEA 加密）。
- 分组时把字节流按**小端 u32 对**解释。

### 5.3 发送方封装流程（`Collector.c: SendCollectorCmd`）

```
1. 组明文帧（§4），算 CRC32 放入帧尾；
2. 动态内层密钥 TempKey:
       TempKey[0..1] = FrameKey[0..1]
       TempKey[3]    = SysTick->VAL   (随机数)
       TempKey[2]    = ~TempKey[3]
3. EncryLen = ALIGN8(CmdLen + 4)          // 明文帧总长向上取 8 的倍数
4. 内层加密: TEA-CBC(TempKey, 帧[0..EncryLen))   // EncryLen 超出实际帧长的部分是填充
5. 把 TempKey[2]、TempKey[3] 共 8 字节附加到密文末尾（offset EncryLen..EncryLen+8）
6. 外层加密: TEA-CBC(FrameKey, 帧[0..EncryLen+8))
7. PPP 转义后加 0x7E 头尾发送
```

### 5.4 接收方解封流程（`Collector.c: CollectorDataFrameHander`）

```
1. PPP 还原得到 length 字节；
2. TEA-CBC 解密(FrameKey, 全部 length 字节)      // 剥外层
3. 取末尾 8 字节为 TempKey[2..3]，TempKey[0..1] = FrameKey[0..1]
4. TEA-CBC 解密(TempKey, length 字节)            // 剥内层（多解密 8 字节无妨）
5. 按 §4 解析校验
```

**要点：内层密钥随帧随机，密文尾部自带密钥；外层是固定密钥。上位机必须逐字节复刻此封装，顺序不能颠倒。**

### 5.5 固件载荷的第四层加密

`0x0B` 数据包里的固件数据在上述三层之外，还用 **FwKey 做 TEA-CBC（零 IV）加密**，由采集器在写入/转发前解密（`Update.c: DecryptData(..., FwKey, ...)`）。

## 6. CRC-32 算法

### 6.1 帧 CRC 与固件 CRC 使用同一算法（GD32 CRC 外设语义）

- 多项式 `0x04C11DB7`，初值 `0xFFFFFFFF`，**按 32 位字（小端取数）MSB 先移位**，无输出异或。
- 等价软实现（工程内注释版参考，`CRC32.c`）：

```c
u32 crc32_mpeg2_wordle(const u8 *data, u32 len /*4 的倍数*/) {
    u32 crc = 0xFFFFFFFF;                    // 首次调用初值
    for (u32 i = 0; i < len/4; i++) {
        u32 w = data[4*i] | data[4*i+1]<<8 | data[4*i+2]<<16 | data[4*i+3]<<24;
        crc ^= w;
        for (int j = 0; j < 32; j++)
            crc = (crc & 0x80000000) ? (crc<<1) ^ 0x04C11DB7 : (crc<<1);
    }
    return crc;                              // 无终值异或
}
```

> 注意：与 PC 侧 `crc32()`（Link 协议用，反射 `0xEDB88320`、有终值异或，即 zlib CRC-32）**不是同一个算法**，两套校验不可混用。

### 6.2 设备端实现细节（联调注意）

设备端 `CRC32_HW()` 直接驱动 CRC 外设寄存器，寄存器**只在 `CRC32_Init()` 时复位一次，之后所有调用（发帧、收帧校验、固件分块校验）都从当前寄存器值续算（链式）**。因此：

1. **固件整体 CRC 是跨包链式**：0x09 下发的 CRC32 = 对所有明文载荷（首包 1040 + 后续各包）链式计算的结果。上位机预计算固件 CRC 时必须用同样的链式语义，不能用"每包独立再异或拼接"。
2. 帧校验语义存在两种可能实现（每帧独立初值 / 全程链式）。**对接现网设备时若第 2 帧起校验失败，请切换为链式模式**（维护一个全局 CRC 状态，按时间顺序对每个明文帧、每个载荷块连续计算，帧 CRC 字段 = 处理完该帧后的寄存器值）。

## 7. 协议 A · 命令集与升级时序

### 7.1 命令一览

| cmd | 方向 | 含义 | param1 | param2 | data |
|---|---|---|---|---|---|
| `0x09` | 采集器→主机 | 请求固件信息（上电轮询） | 1=ARM / 2=DSP | 0 | 无 |
| `0x09` | 主机→采集器 | 固件信息应答 | 1=ARM / 2=DSP | 9 | `[0]`:0=有新固件/≠0=无新固件；`[1..4]`:固件长度 Size(u32 LE，不含 16 字节文件头)；`[5..8]`:固件 CRC32(u32 LE，§6 链式语义) |
| `0x0A` | 采集器→主机 | 准备就绪（ARM：擦除完成；DSP：DSP 擦除完成） | 1=ARM / 2=DSP | 1 | `[0]`=status，0=OK |
| `0x0B` | 主机→采集器 | 固件数据包 | 1=ARM / 2=DSP | 2+载荷长度 | `[0..1]`=包序号 PackID(u16 LE，从 0 起)；`[2..]`=FwKey 加密载荷 |
| `0x0B` | 采集器→主机 | 数据包应答 | 1=ARM / 2=DSP | 1 | `[0]`=status：0=成功请求下一包 / 1=失败 |

### 7.2 数据包规则

- 分包大小：首包载荷 **1040 字节**（= 16 字节固件文件头 + 1024 字节固件；文件头内容由固件打包工具定义，Boot 不解析、写入时跳过），后续包 **1024 字节**，末包 `(Size-16) % 1024` 字节。
- 总包数 `PackSum = ceil((Size) / 1024)`（代码：`(Size-16+1023)/1024`）。
- **停等协议**：每包必须收到采集器 `0x0B` 应答后才能发下一包。
- 包序号不连续 → 采集器置失败且**不应答**（上位机靠超时感知）。
- 全部收完后采集器比对整体 CRC32：一致 → 最后一包应答 status=0（升级完成），并自行把 8 字节 App 头(长度+CRC)写入 Flash；不一致 → status=1。
- 超时：询问固件信息后 **1 秒**未应答放弃；进入收数据阶段后 **30 秒**无数据失败。

### 7.3 ARM 升级时序

```
Boot                          主机
 │ 0x09 (param1=1 请求ARM固件)  →│
 │← 0x09 {0, Size, CRC32}       │   (data[0]=0 表示有新固件)
 │ 擦除 APP 区 (0x0800A000 起)   │
 │ 0x0A (param1=1, status=0)    →│
 │← 0x0B PackID=0 (1040B 密文)   │
 │ 0x0B 应答 status=0           →│   解密→CRC→写 Flash 0x0800A000
 │← 0x0B PackID=1 (1024B)       │
 │        ……循环……              │
 │← 0x0B PackID=N-1             │
 │ 0x0B 应答 status=0/1         →│   CRC 全包比对; status=0 即升级完成
 │ 屏显 "ARM updating:xx%"      │
```

### 7.4 DSP 升级时序（采集器 = 解密转发管道）

ARM 收完后进入 DSP 升级（USART1→DSP，115200-8-N-1）。同样先 `0x09 (param1=2)` 询问，有新固件则执行 DSP 侧握手（`Update.c` 顶部注释 + `DspUpdateTaskFunc`）：

| 步骤 | 采集器→DSP | DSP→采集器 | 说明 |
|---|---|---|---|
| 1 | `01 05 42 00 00 00 00 73 9A` | `48 52`("HR") | 请求进入升级，重试至多 5 次（每次等 2s） |
| 2 | `01 10 04 38 00 02 04 00 00 00 00 C3 DD` | 应答帧 + 等 `43 52`("CR") | Modbus 写寄存器请求擦除，擦除完成最多等 12s |
| 3 | `0A`(param1=2,status=0) →主机 | | 告诉主机 DSP 就绪，开始收 `0x0B` 包 |
| 4 | 每包转发（见下） | `43 52`("CR") | 停等 |
| 5 | `02 00 FF 45 4F 54`("EOT") | | 结束命令，**无论成败都发** |

DSP 数据帧格式（`SendDspFwData`）：

```
[0x02] [AddrH] [AddrL] [载荷≤1024B] [CRC16H] [CRC16L]
Addr   = 0x01FE + 0x00FF × PackID
CRC16  = Modbus CRC-16 (poly 0xA001 反射, 初值 0xFFFF)，高字节在前
```

DSP 固件不经过 ARM Flash；ARM 只负责：解密（FwKey）→ 链式 CRC → 重新组帧转发。DSP 的写入与校验由 DSP 自身 bootloader 完成。

### 7.5 升级总流程（Boot 状态机）

```
上电 ─→ 询问ARM(1s超时放弃) ─→ 有固件? ─擦除→ 收包写Flash ─→ CRC OK? ─┐
        │无/超时                                                      │
        └──────────────┬───────────────────────────────────────────────┘
                       ▼
              询问DSP(1s超时放弃) ─→ 有固件? ─握手/擦除/转发─→ 结束(EOT)
                       │无/超时/完成
                       ▼  (3 秒后)
        ArmPcUpdate: 关协议任务 → LinkRS232Upgrade()  ← PC 刷机窗口(约 1s)
                       ↓ 无连接/结束
        process_app_run(): 配置表 CRC + App 头校验 → GotoApp(0x0800A000+8)
                       ↓ 失败
        留在 Boot 等待 PC 重新刷机（屏显错误）
```

## 8. 协议 B："Link" 刷机协议（PC 上位机）

### 8.1 帧格式（多字节字段为**大端**）

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 4 | 同步字 `"Link"` (0x4C 0x69 0x6E 0x6B) |
| 4 | 2 | link_id（大端） |
| 6 | 2 | data_len（大端，**含尾部 CRC 的 4 字节**） |
| 8 | data_len | 数据 + CRC32（大端，覆盖 `同步字+头+数据-4`，zlib CRC-32：反射 0xEDB88320，初值 0xFFFFFFFF，终值取反） |

### 8.2 link_id 命令表（常用）

| link_id | 方向 | 含义 |
|---|---|---|
| `0x0000` LINK_REBOOT | PC→设备，设备回 | 复位握手；设备回复自身 HWCFG 数据 |
| `0x0011` LINK_START_UPGRADE | PC→设备 | 开始 APP 升级 |
| `0x1111` LINK_START_BOOT_UPGRADE | PC→设备 | 开始 Boot 升级（解锁 Boot 区写权限） |
| `0x0055` LINK_DATA_TRANSFER | PC→设备 | 数据块（见 8.3），设备回 ACK/NACK |
| `0x0022`/`0x1122` TERM_* | PC→设备 | 结束升级 |
| `0x0066`/`0x0077`/`0x0088` | 设备→PC | ACK / NACK / STOP |

### 8.3 数据块格式

```
首块数据开头: upgrade_file_header_t { iSync=0x50790000; iTotalDataLen; }
每块数据:     upgrade_block_header_t {
                  iCRC;        // 块数据(解压前? 按代码为块内数据区)的 CRC32
                  iType;       // 数据类型，见下表
                  iLength;     // 本块压缩数据长度
                  iTotalBlk;   // 该类型总块数
                  iCurBlk;     // 当前块号(从 1 起)
              } + 压缩数据(ENCOMP 私有压缩库)
```

| iType | 数据 | 写入位置 |
|---|---|---|
| `0x50797777` | 配置表 | `ADDRESS_CONFIG_TABLE`(0x08006000)；**必须第一块先发**，否则拒绝 |
| `0x50795555` | ARM APP | 配置表 `iAppAddr`；末块写 App 头(长度+CRC) |
| `0x50792222` | Logo | `iLogAddr` |
| `0x50791111` | 默认参数 | `iDefaultDataAddr` |
| `0x50794444` | 硬件配置 | `ADDR_HARDWARE_CONFIG` |
| `0x5079AAAA` | DSP 程序 | **Bootloader 明确拒绝**（返回错误退出） |

块写入后擦除该类型剩余空间（填 0xFF）；末块校验整包 CRC 并写 App 头。流程：`REBOOT → START_UPGRADE → (DATA_TRANSFER ⇄ ACK)* → TERM → ACK`。

## 9. 上位机最小实现清单（协议 A）

1. 打开串口 9600-8-N-1，等待采集器上电发出的 `0x09` 轮询帧（上电后约 1s 内必须应答）。
2. PPP 解帧 → 外层 TEA-CBC(FrameKey) 解密 → 取尾部 8 字节动态密钥 → 内层解密 → 校验 0xAA/CmdLen/CRC。
3. 收到 `0x09(param1=1)` 后回固件信息帧（加密封装方向相反：明文+CRC → 内层加密 → 附密钥 → 外层加密 → 转义）。
4. 收到 `0x0A` 后按 1040/1024/余数分包，逐包 `0x0B` 停等发送，直到应答 status=0。
5. 待采集器发 `0x09(param1=2)` 再决定是否走 DSP 流程（无 DSP 固件也应答 `data[0]≠0`）。
6. 可复用代码：本工程 `Collector.c / ComProtocol.c / TEA.c / CRC32.c` 可直接移植到采集器 APP 或 PC 工具（C 语言）。

## 10. 遗留问题 / 注意事项

- **帧 CRC 链式问题**（§6.2）：设备端 CRC 外设寄存器全程共享，帧校验语义需与对端联调确认；新对端建议先按"每帧独立 init=0xFFFFFFFF"实现。
- `SendCollectorCmd` 中 CRC 对齐填充字节取自未初始化栈（`u32 cmdbuf[64]`），内容随机但收发双方都只对"实际收到的字节"重算 CRC，不影响正确性；新实现建议填充 0x00。
- 采集器侧 `0x09` 的"有新固件"标志是 `data[0]==0`（**0 表示有**），实现时别反。
- 首包长度校验是 `param2 >= 1042`（2 字节 PackID + 1040 载荷），少于此值直接失败。
- 9600bps 下整包升级耗时较长（1KB/包 ≈ 1.2s 线路时间），进度显示以包计数为准（屏显 `PackCnt/PackSum`）。
