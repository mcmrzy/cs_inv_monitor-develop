一、方案总览（多子域结构）

将单一域名下的流量按类型拆分到独立子域，由阿里云 ESA 分别用最适合的加速类型承载：

域名用途ESA 加速类型回源目标
www.jiuxiaoyw.online管理后台网站页面代理加速 · 网站页面前端容器（nginx）
api.jiuxiaoyw.onlineREST API + WebSocket + SSE + 头像上传代理加速 · API 加速api-gateway
download.jiuxiaoyw.online固件大文件下载 /firmware/*代理加速 · 大文件下载api-gateway（仅 /firmware/）
mqtt.jiuxiaoyw.online设备 MQTT 8883 直连仅 DNS（不加速！）EMQX（直连）
jiuxiaoyw.online（@）根域仅 DNSnginx 301 跳转 → www
*.jiuxiaoyw.online（*）兜底（内部域名等）仅 DNS—
为什么 MQTT 不能走加速？ ESA/CDN 节点只监听 80/443 端口，设备用 8883 端口连接时会连到 CDN 节点导致端口不通、全部掉线。 因此 mqtt 子域必须保持 仅 DNS，让设备直连源站。这就像快递驿站不接收 20 吨的大货车——大件货物只能走自己的专用通道。

三、前置检查：DNS 记录核对表

在阿里云控制台（云解析 DNS）检查以下记录是否齐备：

记录类型值解析方式状态
apiA/AAAA源站两个 IP + IPv6代理加速（API 加速）已配置 ✓
downloadA/AAAA同上代理加速（大文件下载）已配置 ✓
wwwA/AAAA同上代理加速（网站页面）已配置 ✓
@A/AAAA同上仅 DNS已配置 ✓
*A/AAAA同上仅 DNS已配置 ✓
mqttA/AAAA同上仅 DNS（禁止加速）缺失 ✗ 必须补

四、第 1 步：补 mqtt 子域 DNS 记录

1阿里云控制台 → 云解析 DNS → jiuxiaoyw.online → 添加记录
  1. 记录类型：A（如需要 IPv6 再添加一条 AAAA）
  2. 主机记录：mqtt
  3. 记录值：源站两个 IP（与 api/www/download 相同）
  4. 解析请求来源：默认（自动）
  5. 解析方式：仅 DNS（千万不要选代理加速！）
  6. TTL：默认即可

五、第 2 步：EMQX 证书与指纹同步（⚠ 设备在线关键）

此步骤影响设备在线，必须最先处理！ 设备通过 TLS 连接 mqtt.jiuxiaoyw.online:8883 时校验服务端证书与 MQTT_CERT_SHA256 指纹。 若证书不含新域名或指纹未同步，设备 TLS 握手失败 → 全部掉线。
  1. 重新签发 EMQX 证书：证书必须包含 mqtt.jiuxiaoyw.online（SAN），建议直接签通配符 *.jiuxiaoyw.online 一次覆盖所有子域；CA 需为设备信任的标准 CA（保持现状即可）。
  2. 更新服务器 .env.prod 的 MQTT_CERT_SHA256：换成新证书的 SHA-256 指纹。
  3. 同步设备端指纹常量：固件 / App 中硬编码的指纹需同步更新，否则老设备连接会被拒（存量设备见迁移顺序说明）。

六、第 3 步：签发 nginx 通配符证书

nginx 四个 server 块统一使用通配符证书（路径已在 nginx-proxy.conf 中写死）：

2服务器上执行（certbot 需已安装且 80 端口可被 http-01 验证） 
certbot certonly --webroot -w /var/www/certbot \
  -d jiuxiaoyw.online \
  -d www.jiuxiaoyw.online \
  -d api.jiuxiaoyw.online \
  -d download.jiuxiaoyw.online

证书输出目录：/etc/letsencrypt/live/jiuxiaoyw.online/（fullchain.pem + privkey.pem），与 nginx-proxy.conf 中引用路径一致。

七、第 4 步：修改服务器 .env.prod

3编辑 deploy/.env.prod，确认 / 追加以下变量 
# ---- MQTT Broker（设备直连域名）----
MQTT_BROKER=mqtt.jiuxiaoyw.online
MQTT_CERT_SHA256=新证书的SHA256指纹   # ← 必须与新证书一致

# ---- 外部访问域名（多子域 CDN 模式）----
SERVER_URL=https://api.jiuxiaoyw.online
DOWNLOAD_URL=https://download.jiuxiaoyw.online
FRONTEND_URL=https://www.jiuxiaoyw.online

完整字段说明见 deploy/.env.prod.example。其中：SERVER_URL 用于上传文件返回 URL；DOWNLOAD_URL 用于固件下载链接拼接（为空时回退 SERVER_URL）；FRONTEND_URL 用于邀请邮件链接。

八、第 5 步：重新部署

4在 deploy 目录执行 
cd /path/to/deploy
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build

检查各服务健康状态：

docker compose -f docker-compose.prod.yml --env-file .env.prod ps

确认 nginx 配置语法与证书可读：

docker exec inv-nginx nginx -t
首次部署自动迁移上传数据：历史版本 business-api 未挂载持久卷，头像/电站图/固件存于容器可写层（每次部署重建都会清空）。 本次已修复：compose 新增 inv-uploads / inv-firmware 卷，cd.yml 部署脚本会在首次部署时自动执行「备份旧容器数据 → 重建 → 恢复 + 修正属主」的一次性迁移（成功后创建标记 /opt/inv-mqtt/.uploads-migrated，失败保留 /opt/inv-mqtt/data-backup 待人工处理、下次自动重试）。

若绕过 CD 手动部署，请手动迁移： 
mkdir -p /opt/inv-mqtt/data-backup
docker cp business-api:/data/uploads /opt/inv-mqtt/data-backup/uploads
# 更新 compose 后重建容器，再执行：
docker cp /opt/inv-mqtt/data-backup/uploads/. business-api:/data/uploads/
docker exec -u root business-api chown -R app:app /data/uploads /data/firmware

九、第 6 步：阿里云 ESA 加速域名配置

阿里云控制台 → ESA → 为 www / api / download 三个加速域名分别配置（加速类型已随 DNS 记录选定）：

  1. 源站信息：源站类型 IP，填源站 IP（如 183.197.106.187 或 101.43.90.25），端口 443（或 80 + 强制跳转）。
  2. 回源 HOST（最关键）：必须填对应的子域！
    加速域名回源 HOST 填原因
    wwwwww.jiuxiaoyw.online源站 nginx 靠 Host 头分流，填错则落到错误 server 块返回 404
    apiapi.jiuxiaoyw.online同上
    downloaddownload.jiuxiaoyw.online同上
  3. HTTPS：三个加速域名都开启 HTTPS（可用阿里云免费证书，或上传自己的通配符证书）。
  4. 缓存规则建议：
    加速域名路径缓存策略
    download/firmware/*缓存（建议 30 天，固件不可变）
    www/assets/*（静态资源）缓存（带 hash 文件名，可长期缓存）
    www/*（页面）不缓存或短缓存（SPA index.html）
    api/*全部不缓存（动态接口，缓存会导致数据过期）
SSE / WebSocket 回源提示：api 域回源必须透传 Upgrade 头与 text/event-stream（nginx-proxy.conf 已配置）。若 ESA 有 WebSocket/流式回源开关，请开启，否则进度推送 / 实时数据流可能被缓存或截断。

十、第 7 步：管理后台发布（构建参数注入）

前端镜像由 GitHub Actions（.github/workflows/cd.yml）构建，构建时注入子域参数。构建产物中不含相对路径回退之外的任何域名。

5在 GitHub 仓库 Settings → Secrets and variables → Actions → Variables 中配置： 
VITE_API_BASE = https://api.jiuxiaoyw.online
VITE_WS_BASE  = https://api.jiuxiaoyw.online

说明：WebSocket 与 API 同域（api），WS 地址基于同域拼接（代码中默认 /ws 路径自动补到 api 域）。若 WS 需要独立域名，将 VITE_WS_BASE 设为完整 WS URL 即可。

然后推送触发 CD 流水线重新构建并发布前端镜像。

十五、常见问题（FAQ）

Q1：部署到别的服务器 / 换域名还能用吗？

能。所有生产域名均来自环境变量 / 构建参数，未配置时回退同源相对路径。换域名只需修改 .env.prod、GitHub vars 和 DNS，代码零改动。

Q2：本地开发 / 测试环境会受影响吗？

不会。本地未注入环境变量，前端回退 /api/v1、/ws 相对路径，走 Vite 代理；后端 DOWNLOAD_URL 为空时回退 SERVER_URL / 原样返回，与改动前行为一致。

Q3：为什么 api 域不能缓存？

REST 接口数据实时性强（设备状态、告警、遥测），缓存会导致数据过期或串租户。ESA 的 API 加速本身主要做链路优化（TCP 优化、TLS 握手加速），不必开缓存。

Q4：www 域还能直接访问 /api/ 吗？

可以，nginx 为 www 域保留了 /api/、/ws/、/uploads/ 的兼容转发，存量书签 / 老前端不受影响；但新发布的前端会优先走 api 域。

Q5：上传头像走哪个域？

POST https://api.jiuxiaoyw.online/api/v1/upload/avatar。返回的 /uploads/xxx 相对路径由前端 resolveMediaUrl 自动补全为 api 域。

Q6：头像/电站图/固件存哪里？部署会丢吗？

三类文件都存在 business-api 容器的 /data/uploads（头像/电站图）与 /data/firmware（固件）。已修复为 Docker 持久卷（inv-uploads / inv-firmware），容器重建不再丢数据；离线日志存 PostgreSQL（pg-data 卷）。当前规模无需对象存储（OSS/MinIO），若未来扩多副本或磁盘不足再迁移，代码侧 URL 已是相对路径 + 环境变量拼接，迁移成本低。
