📋 1. 概述与背景

1.1 当前 OTA 能力分析

现有的 OTA 升级系统主要包含两种模式：

🌐 在线 MQTT OTA

实现文件：ota_page.dart (741行)

核心能力：

  • 通过 MQTT 通道从云端推送升级命令
  • 支持单芯片固件和升级包模式
  • 实时进度监控和状态反馈
  • 固件预下载功能

限制 依赖网络连接，离线环境无法使用

📡 本地 WiFi OTA

实现文件：local_ota_page.dart (1874行)

核心能力：

  • 连接设备 WiFi 热点进行本地升级
  • 固件通过 HTTP 上传到设备
  • 支持断点续传和进度轮询
  • 设备重启后自动重连机制

限制 需手动连接设备热点，操作步骤繁琐

// 固件完整性校验流程 Future<bool> verifyFirmwareIntegrity(String filePath, FirmwareMetadata metadata) async { // 1. 计算文件 SHA-256 final fileHash = await calculateSHA256(filePath); // 2. 对比服务器提供的哈希值 if (fileHash != metadata.sha256) { throw FirmwareIntegrityException('SHA-256 校验失败'); } // 3. 验证数字签名 final signatureValid = await verifySignature( filePath, metadata.releaseSignature, metadata.securityVersion ); if (!signatureValid) { throw FirmwareIntegrityException('签名验证失败'); } return true; }

📶 5. BLE OTA 详细设计

5.1 BLE GATT 服务定义

新增 BLE OTA 服务，用于固件传输和升级控制：

特征名称 UUID 权限 数据格式 说明
OTA_CONTROL 43534956-4F43-1000-8000-00805f9b34fb 写 + 通知 JSON OTA 控制命令（开始、暂停、取消）
OTA_DATA 43534956-4F44-1000-8000-00805f9b34fb 写 二进制 固件数据传输（分片）
OTA_PROGRESS 43534956-4F50-1000-8000-00805f9b34fb 通知 JSON 升级进度通知
OTA_STATUS 43534956-4F53-1000-8000-00805f9b34fb 读 + 通知 JSON 升级状态查询

UUID 编码说明：

  • 43534956 = ASCII "CSIV"（设备标识）
  • 4F43 = ASCII "OC"（OTA Control）
  • 4F44 = ASCII "OD"（OTA Data）
  • 4F50 = ASCII "OP"（OTA Progress）
  • 4F53 = ASCII "OS"（OTA Status）

5.2 固件分片传输协议

固件文件被分割成小块进行传输，确保可靠性和断点续传：

// BLE OTA 数据包格式 { "seq": 0, // 序列号（0-based） "total": 1024, // 总分片数 "offset": 0, // 数据偏移量（字节） "size": 512, // 当前分片大小 "checksum": "a1b2c3...", // 分片校验和（CRC32） "data": "base64编码的固件数据" }

5.3 MTU 协商与传输优化

为确保高效传输，需要进行 MTU 协商：

参数 推荐值 说明
MTU 512 字节 BLE 4.2+ 最大支持，减少分片数量
分片大小 512 字节 与 MTU 对齐，避免分片
连接间隔 15-30 ms 平衡功耗和传输速率
数据长度扩展 开启 BLE 4.2+ 特性，提升吞吐量
⚠️

性能预估：

MTU 512 字节 + 连接间隔 15ms → 理论传输速率约 34 KB/s

1 MB 固件预计传输时间：约 30 秒（不含握手和校验时间）

5.4 断点续传机制

设备端记录已接收的偏移量，支持中断后继续传输：

1

查询设备状态

连接后读取 OTA_STATUS，获取已接收偏移量

2

跳过已传输数据

从偏移量位置继续发送，避免重复传输

3

逐片校验

每片数据发送后等待设备确认，确保完整性

4

完成升级

所有分片发送完成后，发送升级完成命令

5.5 错误恢复机制

当传输过程中出现错误时，系统自动进行恢复：

// BLE OTA 错误恢复策略 class BleOTAErrorRecovery { static const MAX_RETRIES = 3; static const RETRY_DELAY = Duration(seconds: 2); Future<void> transmitWithRetry(BlePacket packet) async { for (int retry = 0; retry < MAX_RETRIES; retry++) { try { await sendPacket(packet); await waitForAck(packet.seq); return; // 成功 } catch (e) { if (retry == MAX_RETRIES - 1) { throw BleOTAException('传输失败，已达最大重试次数'); } await Future.delayed(RETRY_DELAY); } } } }

⚡ 8. 性能与可靠性优化

8.1 BLE 传输速率优化

通过以下策略提升 BLE 传输效率：

📡 MTU 协商

连接时主动请求 MTU 512，减少分片数量，提升单次传输数据量

⏱️ 连接参数优化

使用较短的连接间隔（15-30ms），增加数据传输机会

📦 数据长度扩展

启用 BLE 4.2+ 的 DLE 特性，支持更大的数据包

🔄 流水线传输

发送数据后不等待确认，连续发送多片数据，提升吞吐量

8.2 WiFi OTA 可靠性

现有 WiFi OTA 已实现的可靠性机制：

机制 实现 说明
热点断线重连 _reconnectDeviceHotspot() 自动检测并重连设备热点
进度持久化 NVS 存储 设备端记录升级进度，重启后继续
超时处理 3 分钟总超时 防止无限等待
状态轮询 1 秒间隔轮询 实时获取升级状态和进度

8.3 固件校验机制

双重校验确保固件完整性和安全性：

1

SHA-256 哈希校验

计算固件文件的 SHA-256 哈希值，与服务器提供的值对比

2

RSA 数字签名验证

使用公钥验证固件签名，确保固件来源可信

3

安全版本检查

验证 security_version 不低于当前版本，防止降级攻击

🔒 9. 安全机制

9.1 固件签名验证

现有系统已实现的安全特性：

✅

已有安全机制：

数据库中的 security_version 和 release_signature 字段

固件上传时强制校验签名和安全版本

安全特性 实现 说明
固件签名 RSA-2048 + SHA-256 每个固件版本都有独立的数字签名
安全版本控制 security_version 字段 不允许降级到低安全版本
完整性校验 SHA-256 哈希 传输前后验证固件完整性
降级保护 版本比较逻辑 设备端拒绝低版本固件

9.2 BLE OTA 安全通道

BLE 升级通道的安全设计：

🔐 BLE 配对加密

使用 LESC（LE Secure Connections）配对，确保链路层加密

🔑 设备鉴权

基于 device_key 的 challenge-response 鉴权，防止未授权访问

🛡️ 防重放攻击

使用 nonce + 时间戳，防止数据包重放

⏱️ 会话超时

连接断开后自动失效，重连需重新鉴权
