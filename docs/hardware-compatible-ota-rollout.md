# 硬件版本兼容 OTA 上线与设备端衔接

## 本次实现

按型号维护标准硬件目录，上传固件时必须多选明确版本。设备云端升级自动匹配；无上报、未登记或不兼容均拒绝。不同硬件可以上传同软件版本的不同文件，同一硬件同模块同软件版本的关联由数据库保证唯一。App 下载缓存范围，本地 BLE/WiFi 上传前读取实际连接 INFO 并匹配。历史记录保存任务创建时原始硬件字符串和固件 ID。

范围规范只 trim + uppercase，不剥离 HW/V 前缀、不推断别名。每份固件的目录代码固定；已发布且范围非空后不可调整，包括停用后。历史空范围允许系统管理员审计后一次补录，不能默认全部通用。

## 部署顺序

1. 备份数据库，执行 `database/migrations/129_hardware_compatible_ota.up.sql`。现有设备的有效非空上报值成为目录条目，原始设备值不改。旧固件不自动分配兼容版本，旧历史快照不伪造。schema.sql 含对应基线增量，但 migrator 仍需在 118 后执行 129，移除旧唯一索引。
2. 发布后端和管理后台；系统管理员在固件库为历史固件补录经过核实的适用版本。目录可在上传表单新增。新固件仍走上传草稿→发布；回退目标必须覆盖源固件全部硬件范围。
3. 发布 App。已下载且缺兼容范围的旧缓存不可直接升级；重新获取元数据并下载。旧客户端不能规避云端检查；已经离线缓存文件的旧客户端需要通过下一阶段设备端保护收口。
4. 实机验证两个硬件分支的远程/BLE/WiFi 升级、错误硬件拒绝、正常重启版本确认、回退及断网恢复。功能测试不替代实机验证。

本次未执行生产迁移、部署、App发布或设备刷写。上线前必须明确旧设备真实硬件值，不可凭当前软件版本推断硬件。

## API

- GET `/api/v1/ota/hardware-versions?model=CS-L10-6K2`
- POST `/api/v1/ota/hardware-versions`：`{"model":"CS-L10-6K2","version":"HW-2.0","description":"第二代主板"}`，系统管理员。
- PUT `/api/v1/ota/firmware/123/hardware-versions`：`{"hardware_versions":["HW-1.0","HW-2.0"]}`，系统管理员。草稿可调整；历史空范围仅一次补录。
- 固件 multipart 的 `hardware_versions` 为 JSON 数组文本。JSON/API响应均为字符串数组。
- 本地结果请求额外携带 `firmware_id`。缺 ID 的历史客户端按型号+硬件+模块+软件版本唯一匹配；指定错误 ID 则拒绝同步，不污染文件身份。
- 概览新增 `hardware_version`、`hardware_state`；模块 `compatibility_reason` 为 `hardware_version_unknown`、`no_compatible_firmware` 或空。

## 第二阶段设备端协议（尚未实施）

现有 `CS_INV_OTA_V1` 签名不包含型号/硬件。本次保留 V1，兼容范围由服务器与新 App 校验，不宣称设备已具备写入前硬件保护。

V2 需由真实固件工程的 OTA 管理器支持并上报 capability，例如 `ota_hardware_manifest_v2`。独立工厂信息保存不可随应用更新修改的型号、板卡/整机硬件标识。升级开始时在擦除/写入前验证受信任签名、公钥、安全版本和本机硬件与清单范围，并把兼容拒绝原因回报云端/App。所有 HTTP/BLE/MQTT 入口共用该校验。缺失身份或V2范围拒绝；每一模块也验证其目标板卡身份。

V2 签名使用版本化、严格规范的清单，建议包括型号、模块、软件版本、文件大小、SHA256、安全版本及明确排序去重的硬件列表；服务器、App和设备必须共享规范编码测试向量。现有V1签名不得被解释为V2。先升级支持V2的引导/管理固件，再逐步将对应设备发布策略切换为必须V2；保留受控兼容窗口而不默认绕过。清单长度须与现有控制帧限制实测对齐，禁止直接向旧512字节接收缓冲塞入无界硬件数组。

验收包括：正确硬件通过、不同硬件及型号拒绝、清单被篡改拒绝、旧客户端离线上传错误文件拒绝、多模块混合/更换板卡、掉电恢复与安全回退。本仓库的外部固件副本不代表实际部署镜像，实施前应确认真实源码、分区和板卡映射。
