1. 系统角色与拓扑

DSP 固件不直接由云端写入。整机链路为：

图 1 · DSP 升级硬件拓扑与职责边界

ARM 在 DSP 升级中的职责

  • 响应 ESP 的固件信息查询（0x09）
  • 与 DSP 握手并触发 DSP 擦除
  • 从 ESP 收密文包（0x0B）并解密
  • 维护链式 CRC32
  • 按 DSP 数据帧格式转发
  • 结束后发送 EOT

DSP 自身职责

  • 响应 HR / 擦除请求
  • 回 CR 表示就绪 / 收包成功
  • 写入自身 Flash
  • 自身 Bootloader 完成校验
  • 升级完成后跳转 App

3. Boot 上电升级总流程

ARM 上电后 Boot 状态机先查 ARM 自身固件，再查 DSP 固件。两路都无新固件或完成后，才进入 PC 刷机窗口并跳转 App。

图 2 · Boot 上电升级状态机（ARM → DSP）
注意：即使本次只升级 DSP，也必须先经过 0x09 p1=1 查询；ESP 对该查询回「无新固件」即可，Boot 会自动进入 DSP 查询。

4. DSP 升级时序（逐步）

当 Boot 收到 0x09 p1=2 的「有新固件」应答后，进入 DSP 路径（源码：Update.c 顶部注释 + DspUpdateTaskFunc）。

图 3 · DSP 升级握手与数据转发时序
步骤 采集器(ARM) → DSP DSP → 采集器 说明
1 01 05 42 00 00 00 00 73 9A 48 52 ("HR") 请求进入升级；重试至多 5 次，每次等 2s
2 01 10 04 38 00 02 04 00 00 00 00 C3 DD 应答帧 + 43 52 ("CR") Modbus 写寄存器请求擦除；擦除完成最多等 12s
3 — — 0x0A (param1=2, status=0) → 主机（ESP），开始收 0x0B
4 DSP 数据帧（见 §6） 43 52 ("CR") 停等；每包必等 CR
5 02 00 FF 45 4F 54 — EOT 结束命令，无论成败都发

5. 握手命令字节详解

5.1 请求进入升级（HR 握手）

01 05 42 00 00 00 00 73 9A
│  │  │           │
│  │  │           └── 校验字节（按 Boot 源码固定序列）
│  │  └── 功能码 / 寄存器相关
│  └── Modbus 风格功能字段
└── 设备地址 / 帧类型

期望应答: 48 52  ("HR" = Handshake Ready)
重试:     至多 5 次，每次等待 2 秒
超时处理: 失败则 DSP 升级中止

5.2 请求擦除（写寄存器）

01 10 04 38 00 02 04 00 00 00 00 C3 DD
│  │  │     │     │
│  │  │     │     └── 数据区
│  │  │     └── 寄存器数量
│  │  └── 起始地址
│  └── 功能码 0x10（写多个寄存器）
└── 地址

期望应答: 标准 Modbus 应答帧 + 等待 43 52 ("CR")
擦除超时: 最多 12 秒

5.3 结束命令（EOT）

02 00 FF 45 4F 54
│     │  └──────── ASCII "EOT"
│     └── 0xFF
└── 0x02

说明: 无论传输成功或失败，都必须发送 EOT
      DSP 收到后结束升级会话

7. 分包与校验规则

7.1 从 ESP 到 ARM 的分包（0x0B，加密通道）

包序载荷大小说明
首包 PackID=01040 B= 16 B 固件文件头 + 1024 B 固件；文件头 Boot 不解析、写入时跳过
后续包1024 B—
末包(Size-16) % 1024不足则按实际长度

总包数：PackSum = ceil(Size / 1024)（代码：(Size-16+1023)/1024）

7.2 校验层次

层次算法校验方
UART 帧校验 CRC32（采集器协议，链式语义） ARM Boot 收 ESP 帧时
固件载荷加密 TEA-CBC（FwKey，零 IV） ARM 解密后转发明文给 DSP
整包 CRC32 对所有明文载荷链式计算 ARM Boot 比对 0x09 应答中的 CRC
DSP 数据帧校验 Modbus CRC-16（0xA001，反射，初值 0xFFFF） DSP Boot 每帧校验
链式 CRC 注意：设备端 CRC 外设寄存器只在初始化时复位一次，之后发帧、收帧、固件分块均从当前寄存器值续算。上位机预计算固件 CRC 必须用同样链式语义，不能「每包独立再异或拼接」。

7.3 停等与序号

  • 每包必须收到 DSP 的 "CR" 后才能发下一包
  • 包序号不连续 → DSP 置失败且不应答（上位机靠超时感知）
  • 末包 CRC 比对通过 → 最后一包应答成功，升级完成

8. 超时与重试

阶段超时 / 重试失败行为
HR 握手（进入升级）2s × 最多 5 次DSP 升级中止
DSP 擦除最长 12s中止
询问固件信息（0x09）1s 无应答放弃该路，继续下一阶段
进入收数据后30s 无数据失败
ESP 等 Boot 0x09（复位后）15s重试触发 ARMU，最多 3 次
ESP 等 Boot 擦除完成（DSP 路径）60s失败（含握手+擦除裕量）
Boot 任意一步超时—回到 NoGetFwInfo 重新查询 0x09

9. ARM 角色：解密转发管道

核心结论：DSP 固件不经过 ARM Flash。ARM 只负责三件事：

11. 联调检查清单

#检查项期望结果
1ARM App 收到 0x07/"ARMU"回 status 0，延时复位进 Boot
2Boot 首发 0x09 p1=1ESP 回「无新固件」（DSP-only 场景）
3Boot 随后发 0x09 p1=2ESP 回 data[0]=0 + Size + 链式 CRC32
4ARM→DSP HR 握手DSP 回 48 52；失败可重试 5 次
5擦除请求DSP 应答 + CR；≤12s
60x0A p1=2ESP 开始发 0x0B 数据包
7数据帧 Addr 递增Addr = 0x01FE + 0x00FF × PackID
8每包 DSP 回 CR停等成立；无 CR 不发下一包
9末包 CRC通过则升级成功；失败发 EOT 并上报
10EOT无论成败都发送 02 00 FF 45 4F 54
11版本上报firmware_dsp 更新为新版本
