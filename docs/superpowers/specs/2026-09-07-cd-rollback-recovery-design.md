# CD 失败恢复设计

## 目标

修复生产 CD 在后端依赖不健康时阻断公网入口、且自动回滚只切换镜像而无法恢复部署配置的问题。部署失败时必须保留诊断证据，并优先保证 Nginx 与管理后台入口可以启动。

## 根因

1. 生产 Compose 把 Nginx、前端、网关和设备服务串成 `service_healthy` 启动链。设备服务的 `/health` 同时检查外部 MQTT，就绪失败会把整个公网入口阻断。
2. CD 在覆盖服务器部署文件后才执行新配置；回滚只恢复 `IMAGE_TAG`，不会恢复上一版 Compose 与配置文件。
3. 失败路径没有输出完整容器状态、Health 详情和关键服务日志，GitHub 页面只能看到 SSH 步骤退出 1。

## 设计

- Docker Compose 健康检查用于进程存活：设备服务改用始终可访问的 `/metrics` 端点；MQTT 就绪状态继续由 `/health` 单独报告。
- API Gateway 不再声明后端启动依赖；前端和 Nginx 只等待直接上游容器启动，避免任一后端健康链阻止公网入口创建。
- Nginx 使用仅监听容器回环地址的 `/livez` 存活端点，探针不再经过域名重定向、CDN 或业务上游。
- 新部署文件先在临时目录组装并校验，再原位覆盖 bind mount 源文件；同步失败时从临时备份原位恢复，完整的旧部署目录单独保留用于运行期回滚。
- 新版本失败时先恢复上一版配置，再恢复上一版镜像标签；恢复旧 Nginx 配置后显式执行配置校验和 reload。
- 从镜像拉取开始注册统一错误处理，失败时输出 `docker compose ps -a`、各容器 Health 状态和关键服务尾部日志。
- 生产部署使用固定并发组串行执行，避免两个 CD 交错改写服务器状态与回滚备份。
- MQTT 未就绪作为明确告警输出，但不让外部服务故障破坏 Web/API 公网入口。

## 验证

- 静态守卫必须拒绝旧版严格依赖、设备 `/health` 容器探针、缺少配置备份/恢复及缺少失败日志的 CD 文件。
- 生产 Compose 通过 YAML 解析和现有 Kafka/Bridge 拓扑检查。
- 在 Docker 可用环境渲染生产 Compose，确认依赖条件和健康命令符合设计。
- 推送后检查 main CI、CD 以及生产域名真实 HTTP 状态。
