# 手机 App 设备固件升级界面设计

## 背景与目标

当前 App 的 OTA 首页以“检查更新、本地升级、固件库、升级历史”四个工具入口组织，并在固件展示中直接使用 ESP、ARM、DSP、BMS 等芯片名。新界面要改为用户能理解的设备与功能视角：先选择自己的设备，再查看该设备的基础信息、各功能模块固件版本、更新说明与历史记录。

本次主要调整 Flutter App 的信息架构、页面、路由和客户端数据读取。为让更新日志直接返回真实发布说明，后端设备级 OTA 历史响应增加一个只读 `changelog` 字段；这是向后兼容的响应扩展，不修改数据库结构或固件协议。

## 用户可见命名

整个 OTA 用户流程不再展示 ESP、ARM、DSP、BMS 缩写，包括首页、设备固件详情、检查结果、可用版本、固件资源、升级进度、升级历史和本地升级。客户端仍以原始字段和 `target_chip` 值完成接口映射，但所有用户可见文本统一通过一个固件模块展示映射转换为：

| 后端标识 | 用户可见名称 | 功能说明 |
| --- | --- | --- |
| `esp` / `firmware_esp` | 通信采集 | 设备联网、数据采集与云端通信 |
| `arm` / `firmware_arm` | 系统主控 | 整机协调与系统逻辑 |
| `dsp` / `firmware_dsp` | 功率控制 | 逆变、充放电与功率调节 |
| `bms` / `firmware_bms` | 电池管理 | 电池监测、保护与均衡 |

未知 `target_chip` 不回显原始值，统一显示“设备组件”。映射提供模块名称、说明和图标语义，供所有 OTA 页面复用；中文和英文均由现有本地化资源提供。英文名称分别为 Communication, System Control, Power Control 和 Battery Management，同样不出现芯片缩写。

## 页面结构

### 设备固件升级首页

- 页面标题由“OTA 升级”改为“设备固件升级”。
- 顶部只显示接口返回的准确设备总数，不根据当前页伪造在线/离线聚合统计。
- “我的设备”列表作为主入口。每项显示设备名称、型号、序列号、在线状态，点击进入该设备的固件详情。设备名称按 `alias → model → sn` 回退，避免出现空标题。
- 原有四项能力保留在设备列表下方的次级功能区，并优化为：
  - 检查全部更新：检查所有在线设备是否有可用更新。
  - 近场连接升级：通过蓝牙或设备热点完成本地升级。
  - 固件资源：按设备型号浏览可用版本并预下载。
  - 全部更新记录：查看用户可见设备的所有更新结果。
- 支持下拉刷新；加载、空数据和失败状态沿用 App 现有统一组件。
- 设备列表使用 `GET /devices` 的 `page/page_size` 分页结构，首屏读取 20 条，滚动到底继续加载，直到已加载数量达到 `total`。状态 `1`（在线）和 `2`（故障但在线）都显示为在线，其余显示离线。

### 单台设备固件详情

页面顺序固定为：

1. 设备摘要：名称、在线状态和型号。
2. 设备信息：型号、名称、设备序列号、硬件版本。
3. 固件详情：通信采集、系统主控、功率控制、电池管理四张卡片。
4. 固件更新日志：按时间倒序展示该设备的升级记录。
5. 页面底部固定“检查固件更新”主按钮。

固件卡片显示当前版本。版本字段为空时不显示伪造版本：

- 普通模块显示“版本未上报”。
- 电池管理的 `firmware_bms` 非空时只说明设备上报了该版本，可以展示版本号；为空时只显示“版本未上报”。初版没有可靠的接入和兼容能力字段，因此不显示“未接入”或“此型号不支持”，也不从 SOC、电压、`battery_type` 或非空版本推断可升级能力。
- “最新”或“可更新”只来自检查更新接口的明确结果；设备详情字段本身不推断版本新旧。

### 固件更新日志

日志使用升级任务与版本说明的合并时间线。每项展示：

- 更新时间；
- 功能模块名称；
- 原版本到目标版本；
- 成功、失败、进行中或已取消状态；
- 固件发布说明；
- 失败时的错误信息。

列表首屏加载最近 10 条，详情页展示前三条；“查看全部”进入 `/ota/device/:sn/history` 单设备完整历史页并分页加载。数据来自设备级历史接口 `GET /ota/devices/:sn/history?page=&page_size=`。后端在该查询中以 `firmware_id` 左连接 `firmware_versions`，为每条记录增加 `changelog`；没有匹配固件或说明为空时显示“暂无更新说明”，绝不关联其他版本的说明。

## 数据流与路由

- 首页通过 `DeviceRepository.getList(page, pageSize)` 获取用户可见设备，并在页面级聚合状态中维护分页、刷新和加载更多；不改变全局 `DeviceBloc` 的列表语义。
- 设备详情页拥有独立聚合状态，分别维护设备信息和历史列表的 loading/data/error，保证局部失败互不覆盖。
- 设备详情通过 `DeviceRepository.getDetail(sn)` 获取完整响应。设备字段来自 `data.device`；在线状态优先使用 `data.online_status.online`，缺失时才回退到 `device.status == 1 || device.status == 2`。显式 `false` 不被数据库状态覆盖。
- OTA 数据层新增 `getDeviceFirmwareHistory(sn, page, pageSize)`，返回 `DeviceFirmwareHistoryPage`，其中包含强类型的 `items`、`total`、`page` 和 `pageSize`。单项包含固件 ID、模块、原版本、目标版本、状态、进度、错误、更新说明和各时间字段。
- 已知历史状态映射为：`pending` 等待更新、`downloading` 下载中、`transferring` 传输中、`verifying` 校验中、`upgrading` 更新中、`success/completed` 更新成功、`failed` 更新失败、`cancelled` 已取消；未知状态显示“状态未知”，不回显内部状态码。
- “检查固件更新”复用现有 `/ota/:sn` 检查与升级页面；设备固件详情只负责信息聚合，不复制升级状态机。
- 新增设备固件详情路由 `/ota/device/:sn`，并以路由测试验证它解析到新详情页、`/ota/:sn` 仍解析到原检查页，不依赖未经验证的路由顺序假设。
- 原 `/ota/check-all`、`/local-upgrade`、`/firmware-library`、`/upgrade-history` 路由继续保留。

## 状态与错误处理

- 设备离线：允许查看已返回的设备信息和历史，检查按钮置为不可执行并给出“设备离线，暂时无法检查”的说明。
- 设备详情失败：显示统一错误态和重试按钮，不展示空白固件卡片。
- 历史加载失败：设备与固件信息仍可展示；日志区域单独显示失败与重试，不让局部失败阻断整页。
- 无历史：显示“该设备暂无固件更新记录”。
- 检查更新失败：沿用现有 OTA 页错误处理。
- 无设备：首页显示空状态，并保留近场连接升级入口。

## 测试与验收

采用 Widget 测试先行，至少覆盖：

- 首页标题为“设备固件升级”，设备列表位于次级工具之前，点击设备进入对应详情路由。
- 首页仍能进入检查全部更新、近场连接升级、固件资源和全部更新记录。
- 详情页显示四项设备信息和四个功能模块名称，页面文本不出现 ESP、ARM、DSP、BMS。
- 固件字段正确映射到四个功能模块，缺失版本显示保守状态。
- 更新日志按设备读取，展示版本变化、状态、时间和来自同一 `firmware_id` 的说明；空列表与局部失败可恢复。
- 在线设备可点击“检查固件更新”，离线设备按钮不可执行并显示原因。
- 中英文新增文案均进入现有本地化资源；两种语言的 OTA 页面都不显示芯片缩写或未知原始模块值。
- 后端设备级历史返回正确的 `changelog`，且固件记录不存在时安全返回空说明。
- 后端仓库测试覆盖 `LEFT JOIN` 命中、已下架但仍存在的历史固件，以及空说明归一化。当前外键禁止构造不存在的固件引用；未命中的 `LEFT JOIN` 仅作为防御性查询语义保留，不通过破坏约束来制造测试数据。

完成后运行相关 Widget/路由/映射测试、后端历史查询与 handler 测试、`flutter analyze`、Go 测试及静态检查，并检查格式化与局部差异。真实后端联调或实体设备升级不由静态测试替代；若当前环境无法启动后端，应明确标记端到端验证未覆盖。
