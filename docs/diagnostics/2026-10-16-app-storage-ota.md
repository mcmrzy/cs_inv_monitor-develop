# App 储能显示与 OTA 排查记录（2026-10-16）

## 已确认的原因与修复

1. 单台逆变器的能量流用电压乘电流计算电池功率。存在已上报充放电功率、但电流缺失的合法数据，因此实测 600 W 会显示成 0 W。改为优先使用实测功率，只有未上报功率时才使用有效电压和电流计算；缺失或过期读数显示 `--`，真实 0 保留。
2. 电站能量流没有持续获取当前数据。增加每 60 秒的网络刷新；单设备订阅其新数据，全部设备继续使用服务端授权范围内的汇总。后台、被其他路由覆盖或本地连接模式暂停网络轮询。单设备快照到期时主动失效一次，即使网络刷新失败或响应没有变化，也显示 `--` 并停止对应流向；下拉刷新会重新请求所选设备。
3. 服务端把过期 BMS 快照的 `bms_online` 置为 0，App 将其解释为断连。服务端增加 `reported_bms_online` 保留最近一次报告的连接证据，同时保留原有效性门槛，过期数据不能重新用于实时读数或告警。App 区分数据过期、状态未知和通信设备离线。
4. 普通远程 OTA 服务端已取消强制硬件档案门槛，App 仍根据未知硬件自行生成拒绝原因并禁用升级。移除普通远程入口的本地硬件门槛，继续服从服务端型号、目标模块、发布、灰度、权限和拒绝原因。服务端明确允许的未上报当前版本模块也能进入升级确认。可信本地 OTA 的校验保持原要求。
5. 失败任务在设备离线时重试，未清空上一轮 `last_dispatched_at`，可能在新尝试尚未下发时就被超时收口。两个重试入口均清空此字段；首次重新下发后再开始新一轮确认超时。

## 补充：DSP 人工重试被防重放拦截

用户提供：设备 `H1ZZX00139000101`，通信采集版本 `0.6.32-ota-confirm`，目标功率控制（DSP）`1.1.50`，进度 0%，错误 `TASK_REPLAY_BLOCKED`。

本机对应固件源码 `D:/CS_INV_WIFI/esp32_arm_replacement/main/ota/ota_service.c` 的 `reserve_manifest()` 会先调用 `storage_claim_direct_ota_task()`，为 DSP/BMS 持久保存已接收的任务编号；历史编号再次启动会被拒绝。MQTT 适配器原样保存和回传字符串 task_id，编号限制允许本次使用的字母、数字和连字符。

云端人工重试虽然递增 `retry_count`，却一直发送相同的数字记录 ID，因而与设备保护冲突。修复为：

- 初次尝试保留数字编号，例如 `123`；第 1、2 轮人工重试分别用 `123-r1`、`123-r2`。数字 `upgrade_id` 和父任务 ID 不变。
- 同轮自动补发仍发送相同编号，保留设备防重放与幂等保护，不关闭固件校验、不清除设备存储。
- 下发领取同时检查预期 `retry_count`，旧发送协程不能领取新一轮任务；同父任务重复发起时读取数据库实际次数，并清空旧下发时间。
- ACK/状态回报严格绑定设备、记录、次数与活跃状态。显式编号无匹配时不回退到其他任务；无编号旧协议只兼容首次尝试。格式错误返回 400。
- 成功回写的模块、版本、父任务统计与后续升级包处理，绑定实际更新的记录，避免按“最近成功记录”写错模块。

回归证据：修复前重试编号始终为 `123`；旧发送请求可领取新一轮任务；成功回报可能错误读取另一条 ARM 成功记录。以上场景均有修改前失败证据，修改后通过。隔离 PostgreSQL 覆盖 30 个 ACK/状态组合、两个成功后续处理场景、进度持久化及 5 项投递/迁移集成测试；通信层验证重试字符串在两种消息格式中原样转发。

最终 business-api 全包编译、vet 和普通测试通过；本机测试日志保存于 `.tmp/task-replay-api-final-elevated.log`、`.tmp/task-replay-handler-final.log`。因当前沙箱禁止回环网络，涉及测试自身 HTTP 服务和隔离 PostgreSQL 的验证使用已获准的执行方式运行。没有连接生产数据库。
