单设备调试模式与电压电流曲线

目标：在 App 和管理后台对指定设备开启临时调试，使设备每 30 秒生成并上报一次新的运行快照；按指标选择曲线，查看 MPPT、电池、逆变、负载相关电压和电流。

范围：云端设备模式、MQTT 命令、设备固件、原始时序查询、Web 与 Flutter。本文是实施方案，尚未修改业务代码。

1. 现状与关键发现

现行协议docs/CS-L10-6K2_MQTT_上报协议设计_V2.1.md 定义 cs_inv/{sn}/heartbeat、57 值 V2.1 快照，标称 180 秒；旧 docs/MQTT接口文档.md 是多主题 5 秒方案，不能直接套用于新型号。
代码与文档频率冲突当前可见的 ESP32 副本在 main/app/config.h 将 TELEMETRY_PERIOD_MS 设为 30000；telemetry.c 已每 30 秒发 heartbeat。仅改 App/Web 刷新不会实现“开启后才 30 秒”。须先确认生产固件实际版本。
已有数据链路设备服务解析 V1/V2 heartbeat，写 device_telemetry_3min、device_latest_state 和 Redis。表名含“3min”，实际按每条 heartbeat 写入；现有 GET /devices/by-sn/:sn/telemetry 会整段查询再分页，不适合调试曲线。
已有 UI 与图表库Web 设备详情的实时 Tab 每 10 秒查询最新值，已依赖 ECharts；App 实时页默认每 60 秒轮询，已依赖 fl_chart。两端可复用依赖，但应新增专用的原始样本接口。
目前没有“设备级调试模式”：Web 的“全部参数（调试）”只是展开字段；Flutter 的 kDebugMode 是开发构建开关；固件的 query_telemetry 只触发一次补报。不能把这些当作本需求的启停开关。

命令链路已经存在：POST /devices/by-sn/:sn/control → DeviceService.SendPreparedCommand → Device Server 内部 HTTP → cs_inv/{sn}/cmd → cmd/response。但当前“已发送”只表示已投递，不代表设备已经切换频率；固件处理 query_telemetry 时也是先回 OK 再等待下一次 tick 发样本。

2. 目标、假设与数据语义

  • 范围：每次仅操作路径中的一台设备 SN；App/Web 看到同一会话状态，关闭任一页面不自动停止设备调试。
  • 频率：设备侧以 30 秒周期重新读取/获取运行参数并上报 heartbeat。前端每 10 秒读取新增样本是界面刷新频率，两者不是同一概念。
  • 时长假设：每次开启默认 60 分钟，服务器与固件都设置绝对过期时间；本期只允许固定 30 秒，不开放任意高频配置。时长与并发上限可在实施前调为运营参数。
  • 权限：查看沿用设备数据归属；开关沿用 devices:control 加设备归属。所有操作者共享设备状态，保留操作者与来源审计。
  • 支持范围：先支持已确认 heartbeat V2.1 且可升级 ESP32 固件的型号；其他型号显示“不支持调试频率切换”，不能只开启网页计时器。
  • 历史范围：曲线默认显示当前会话最近 60 分钟，首屏最多 120～140 点；可在会话内切换 15/30/60 分钟。仅提供会话内原始采样，不把 3 分钟聚合值标成 30 秒点。

字段核对：四组曲线的真实来源

图上分组电压线电流线语义与可交付性
MPPT / PV1pv1_voltagebuck1_current当前电流是 Buck1 电流，不等于已证实的 PV1 输入电流；PV2 可选 pv2_voltage + buck2_current。界面必须按原名标注。
电池battery_voltagebattery_current可直接交付。电流充电为正、放电为负，零值是有效数据。
逆变相关dc_bus_voltageinv_current分别是直流母线电压和逆变电流，不是同一测点的电压电流对；只能按这两个真实名称呈现。
负载 / 交流输出ac_output_voltage（落库别名可能为 ac_voltage）output_current（落库别名可能为 ac_current）已有的是设备交流输出测点，可用作负载侧参考；协议没有独立负载端传感器字段。
需求边界：若“MPPT 电流”“逆变电压”“负载电压/电流”必须是各自独立物理测点，则现有 V2.1 还缺输入电流、逆变桥电压和独立负载端数据源。实施流程 1 必须先由固件/硬件确认寄存器或传感器；有来源再按协议追加字段、迁移和解析，不允许把 Buck 电流、母线电压或交流输出值改名充数。确认前的首版仅展示上表可证实的曲线与说明。

3. 端到端架构

Web / App 开启→Business API 会话状态机→Device Server→MQTT 单 SN 命令→ESP32 30 秒采样→heartbeat V2.1→现有解析/存储→调试样本 API→两端曲线

数据与模式分离

device_debug_sessions 只保存调试意图与生命周期：id、device_sn、request_id、status、interval_seconds、started_at、expires_at、stopped_at、requested_by、source、start_task_id、stop_task_id、last_sample_at、failure_reason、created_at/updated_at。(device_sn,request_id) 唯一。曲线点继续写现有 device_telemetry_3min，首版无需复制一张遥测表。

新增按 (device_sn,event_time) 的有界原始查询：只投影列入白名单的时间、电压、电流、quality_flags 和协议版本；以 session.started_at 和 expires_at 限定范围，按时间和 data_hash 稳定排序，游标增量返回。不得调用现有先全量加载再分页的 GetTelemetryData。现有 90 天遥测保留策略仍适用；如果后续要求短期删除调试样本，再单独设计分表与留存规则。

设备固件行为

  1. 新增设备命令 set_debug_telemetry；参数建议为 args=[enabled,30,duration_seconds]，固件当前只解析 args[0]，须扩展解析并校验全部参数。关闭时 enabled=0，设备恢复实际发布的默认周期。
  2. 设备仅在 MQTT 在线且 ARM 运行参数可用时确认启用；回执包含 task_id、结果、effective_interval_seconds 和设备侧到期时间。设备端使用单调时钟管理本次剩余时长，不因 NTP 回拨无限延长。
  3. 每周期必须取得新采样时间；不能把同一份 30 秒以上的缓存重复写成“实时点”。ARM 未应答时跳过本点并上报故障，不做过期快照补发。
  4. 固件重启、到期、云端停止、恢复出厂均回到默认周期；调试开关不持久化为永久配置。开始/停止命令幂等，重复 task 不反复重置到期时间。
  5. 在当前本地固件副本中默认常量已经是 30 秒；如果生产也如此，必须先将正常模式恢复为经确认的基线（协议文档为 180 秒），再发布支持模式切换的固件，否则开关没有效果。
吞吐估算：单台设备 60 分钟调试约 120 条 heartbeat；若正常为 180 秒，同段原本约 20 条，增量约 100 条。上线前按计划并发上限压测 MQTT、Kafka、解析、数据库与 API 查询，不用单机理论值代替实测。

4. API 契约与状态机

方法与路径输入 / 返回关键语义
GET /api/v1/devices/by-sn/{sn}/debug-session当前会话、能力、有效频率、结束时间、最后样本时间、失败原因。设备数据权限；Web/App 共用。
POST /api/v1/devices/by-sn/{sn}/debug-session{"duration_seconds":3600,"request_id":"UUID"}；返回 session_id、status、task_id。只允许在线且支持的设备；相同 request_id 幂等；同设备已有活动会话返回现有会话或 409。
DELETE /api/v1/devices/by-sn/{sn}/debug-session/{id}返回停止中的会话；重复关闭幂等。控制权限；离线时状态标为待确认/中断，固件 TTL 最终收敛。
GET /api/v1/devices/by-sn/{sn}/debug-samples?session_id=...&after=...&limit=100{items:[{time,received_at,quality_flags,metrics:{...}}],next_cursor,...}仅查询该 SN、该会话、有界时窗；limit 上限 200，禁止任意 SQL 字段名与任意无限时间区间。
设备命令建议格式（最终写入契约并由固件联调确认）
cs_inv/{sn}/cmd  QoS 1  retain=false
{"v":2,"t":<unix秒>,"task_id":"<uuid>","cmd":"set_debug_telemetry","args":[1,30,3600]}

设备回执：cs_inv/{sn}/cmd/response
{"task_id":"<uuid>","cmd":"set_debug_telemetry","result":"OK","err":0,
 "effective_interval_seconds":30,"expires_at":<unix秒>}

现有 API 命令代码会为有 schema 的命令带 v=1；上例的 v=2 仅是目标协议草案，实施时必须让 Business API、Device Server 与固件使用同一值，不能单独改固件。expires_at 需要由 Device Server 透传到 MQTT 的话也要显式补齐；设备端仍以接收后的 duration 为准。

状态转换

idle→starting→active→stopping→stopped / expired
  • starting：事务写会话并下发命令；只有收到该 task 的成功回执，且 75 秒内看到新采样，才显示 active。单纯 HTTP 200/MQTT 已投递不算启用成功。
  • active：样本迟到超过 75 秒显示“数据中断”；允许补样本恢复。设备离线则标记 interrupted，不排队旧开启命令；恢复连接后须重新开启。
  • stopping：收到停止成功回执后 stopped；失败则给出待确认状态和最终到期时间。服务端定期扫描过期会话、发送在线停止命令；设备本地 TTL 为最终兜底。
  • 并发控制：数据库事务或按 SN 的锁保证同一时刻只有一个未结束会话；部分唯一索引约束 starting/active/stopping；API 重试与 App/Web 同时点击不会创建多个设备定时器。
安全要求：调试命令不能走当前普通命令“离线入 Redis 队列、稍后补发”的路径。过期后才送达会造成意外高频上报；Device Server 应对该命令离线返回明确错误，Business API 不得转为 queued。

5. 分流程实施

流程 1：协议与测点定稿

涉及文件：contracts/openapi/device-debug-v1.yaml、固件 config.h、现行 MQTT 协议文档。

修改说明：确认量产固件的 heartbeat 默认周期和可升级范围；逐一记录 PV 输入、Buck、母线、逆变桥和负载端的物理测点/寄存器/单位。如果硬件有独立新测点，先追加协议字段定义和版本能力位，再排迁移、解析与曲线；没有则固定使用第 2 节的真实字段名称与提示。确定 60 分钟 TTL、同时开启设备数上限和允许角色。

流程 2：设备侧切换与回执

涉及文件：ESP32 main/app/config.h、main/telemetry/telemetry.c、main/telemetry/cmd_handler.c；如有新增物理量，再涉及 ARM 寄存器读取与 V2 解析器。

修改说明：把默认频率与调试频率分开；解析三参数命令、执行幂等切换、单调 TTL 与断电恢复；按 30 秒新鲜运行参数发送 heartbeat，保留既有告警与 OTA 优先级。固件版本/能力返回是否支持此命令，避免旧设备误显示开关。

流程 3：后端会话、存储与样本接口

涉及文件：上表迁移、database/schema.sql、Business API 的 model/repository/service/handler、business-api/cmd/main.go、Device Server 命令路由/MQTT 通道。

修改说明：新增设备级状态机和受保护路由；复用命令审计表并关联 task；在回执消费处推进会话；会话协调任务仅对活动 SN 查询最新入库 heartbeat，确认首次新样本、更新 last_sample_at 并处理到期/中断。新样本接口直接读 device_telemetry_3min 的类型列，严格白名单、时间窗、游标、查询超时；按 quality_flags 标示无效/乱序点，不以 0 替代 null。对确有新测点的型号，新增只增迁移并同步 telemetry_field_catalog 与型号能力。

流程 4：管理后台

涉及文件：device-detail/index.tsx、新增 DebugTab.tsx、deviceApi.ts、queryKeys.ts、locales/deviceDetail.ts。

修改说明：在设备详情新增“设备调试”Tab，展示设备 SN、模式状态、剩余时间、实际最新样本时间、启停按钮及字段来源提示；ECharts 分电压 V / 电流 A 两个纵轴，按量测分组勾选曲线。隐藏浏览器页面时停止数据轮询，回来先查服务端状态和增量点；不因关 Tab 自动关闭设备模式。

流程 5：Flutter App

涉及文件：device_realtime_page.dart、app_router.dart、新增 device_debug_api.dart / device_debug_page.dart / device_debug_chart.dart、三处 l10n 文件。

修改说明：从单台设备实时页进入调试页，状态与 Web 一致；使用 fl_chart 绘图、Chip 多选曲线、时间窗选择。App 退后台暂停拉取，回前台按游标补点；网络断开保留已见曲线并标记中断。当前 App 存在局域网直连模式，该页面应明确“云端调试需要设备在线”，不把本地 3 秒轮询误写成云端 30 秒上报。

流程 6：端到端联调

涉及文件：对应 Go、Web、Flutter 测试文件及固件主仓测试。

修改说明：先用模拟器覆盖成功/拒绝/超时/重复回执，再用一台可升级设备核对 30 秒真实采样、双端曲线、停止后的默认周期。最后测试多台设备隔离与预定并发上限。

6. Web 与 App 的共同交互规格

顶部控制区显示“未开启 / 正在开启 / 已开启 / 数据中断 / 正在关闭 / 已过期”，设备 SN、30 秒采样、自动关闭倒计时、最新样本本地时间。启停按钮带请求中禁用与错误提示。
曲线选择四组入口；每条线可单独勾选与取消，支持“全部清除”，默认选电池电压/电流与交流输出电压/电流。MPPT1/2 分别命名，Unsupported 的线不可选并说明来源。
图表尺度同一时间轴，V/A 双纵轴或手机上电压、电流上下两张同步图；单位写在轴标题和悬浮提示中。电池负电流可过零；横轴按用户时区展示，数据以 UTC 存储。
数据质量缺值断线、不连零点；质量标志异常和超过 75 秒间隔显示缺口/提示；按 event_time 排序、按游标去重，不平滑跨过断档。

首屏获取当前会话最近 60 分钟原始点，之后每 10 秒增量拉取；每次请求都校验会话 id 与 SN。单页只保存约 200～240 点的环形缓冲，长时间会话通过服务端再次查询指定窗口。启停结果可在另一个客户端 10 秒内同步可见。

7. 测试与验收

顺序验证点通过标准
1协议/固件单测未开启按生产默认周期；开启一台后只该 SN 约每 30 秒一条新 heartbeat；到期/关闭/重启恢复默认；非法参数、重复命令、无 ARM 数据均有确定结果。
2后端权限与并发无归属或无 control 权限为 403；离线开启明确失败且不会延后执行；两个客户端同时开启仅一个会话；停止和重试幂等；不同 SN 互不影响。
3原始时序返回顺序、单位、负电流、零值、null、乱序/重复、时区与游标均正确；长查询被限制；未暴露 raw envelope；30 秒采样没有被 3 分钟聚合。
4Web/App 行为双端看到相同状态；能独立开关每一条可用曲线；关闭页面后设备模式由 TTL 维持；重新进入可恢复曲线；背景/离线显示明确。
5实机与负载用设备时间戳核对连续样本间隔目标 30 秒，允许网络抖动；停止后实测恢复默认周期。并发上限下消息摄入、数据库写入、样本接口延迟满足上线目标，实际目标值以压测记录定稿。

8. 实施前确认项、交付顺序与工作量

必须确认的三件事：① 生产 ESP32 固件的默认上报频率究竟是协议中的 180 秒还是本地副本的 30 秒；② MPPT 输入、逆变桥、独立负载端是否存在真实测点，以及地址与单位；③ 允许开启调试的角色、单次时长和并发设备上限。确认后再冻结接口与固件协议。

建议交付顺序：协议/测点清单 → 固件开关及自动到期 → 服务端会话与有界样本 API → Web 调试页 → App 调试页 → 实机与并发联调。若新增真实测点，协议和数据库解析工作插入在固件与 API 之间。

粗估：在不新增硬件测点、可直接修改并构建固件的前提下，后端与数据接口 3～5 人日，固件 2～4 人日，Web 2～3 人日，App 2～3 人日，测试/实机联调 2～3 人日，总计约 11～18 人日；真实测点扩展、固件仓整合和生产环境部署另计。估算以协议和设备能力确认后重算。

本方案的文件级落地摘要：契约定义唯一语义；迁移保存设备会话；Business API 负责权限、状态、样本；Device Server 保证调试命令即时性；固件负责真正的 30 秒采样与超时恢复；Web/App 分别通过已有 ECharts / fl_chart 实现可选曲线，统一从服务端读取模式和采样。
